# 환불 규정 문구 및 블로그 유형 삭제 구현 계획

> **작업 에이전트:** 구현 승인을 받은 뒤 `superpowers:executing-plans`로 작업별로 진행한다. 아래 체크박스는 아직 수행하지 않은 구현 작업이다. 이 문서 작성은 구현·DB 변경·배포 승인이 아니다.

**목표:** 첨부본의 환불 문구를 교체하고, 연결된 글이 없는 블로그 유형을 기본 유형까지 삭제할 수 있게 한다. 삭제 결과는 어드민과 사용자 웹의 블로그 유형 목록에 함께 반영한다.

**구조:** 환불 규정의 목록 항목 한 개를 교체한다. 유형 삭제는 기존 선택 컴포넌트와 대화상자를 재사용한다. 고정 상품 유형을 직접 지우지 않고 블로그 전용 삭제 내역을 서버에 저장해 다시 접속해도 삭제 결과를 유지한다.

**기술:** Next.js 사용자 웹, React/Vite 관리자 웹, TypeScript, 기존 Base UI AlertDialog, 공용 Supabase 접근 패키지, PostgreSQL.

**요구 근거:** 사용자가 첨부한 이미지 1·2·3과 임시저장 글의 삭제 차단 조건·문구·버튼을 지정한 후속 답변. 추가 지시에 따라 삭제 버튼은 각 유형 오른쪽에 표시하고, 팝업 제목은 간단하게 정하며, 사용자 웹에도 유형 삭제를 반영한다. 와이어프레임은 총 2장으로 나눈다. 이미지 1과 3은 같은 환불 문구 수정 요청이다. 현재 실행 범위는 계획과 와이어프레임 작성이다.

## 공통 제약

- 구현 전 `design.md`와 관련 기존 컴포넌트를 확인한다. 사용자의 최신 지시에 따라 와이어프레임 PNG 총 2장을 제시한다. 첫 장은 첨부 1·3번의 환불 문구, 둘째 장은 첨부 2번의 어드민·사용자 웹 변경이다. 각 장은 흰색 가로 캔버스에 Desktop과 Mobile을 나란히 표시한다. 승인 후에만 구현 코드를 수정하고, 미정 사항은 `확인 필요`로 표시한다.
- 지정되지 않은 삭제 버튼 위치·아이콘·크기·간격·모바일 동작·팝업 문구·알림을 만들지 않는다. 기존 공용 패턴의 필요한 부분만 재사용한다.
- 기존 글·본문·이미지·상품·포트폴리오 유형을 삭제하거나 수정하지 않는다. 기본 유형의 공용 원본인 `productTypes`도 유지한다.
- 새 브랜치, 커밋, 배포, 운영 DB 변경은 이 계획 작성에 포함하지 않는다. 시뮬레이터·에뮬레이터를 실행하지 않는다.
- 이번에는 소스·설정·테스트를 수정하지 않는다. 작업 시작 당시 `git status --short`와 `git diff --stat` 출력은 비어 있었다.

## 확정된 변경 내용

### 1. 환불 규정의 항목 한 개 교체

경로는 `/refund-policy`이며, 제3조 → `② 이용자 귀책사유 (환불 불가)`의 해당 항목만 교체한다.

교체 문구:

> 인쇄물의 특성상 모니터 색상(RGB)과 인쇄 색상(CMYK) 차이
> (모니터 화면과 실제 인쇄물은 색상 표현 방식이 다르며, 용지·잉크·코팅 등 제작 조건에 따라 색상 차이가 발생할 수 있습니다.)

다른 환불 조건, 시행일, 제목, 목록 순서, 폰트와 여백은 유지한다. 첨부본의 줄 나눔이 강제 줄바꿈을 뜻하는지는 확인되지 않았으므로 임의의 `<br>`나 추가 문단을 넣지 않는다. 화면 너비에 따른 기존 줄바꿈을 유지하는 안으로 와이어프레임에 명시한다.

### 2. 블로그 유형 삭제

기본 유형과 직접 추가한 유형에 같은 삭제 조건을 적용한다. 각 유형의 오른쪽에 `삭제` 버튼을 표시한다. `전체`는 필터 전용 값이므로 삭제 대상 유형에 포함하지 않는다. 사용자가 제목 작성을 위임했으므로 차단 팝업 제목은 `삭제 불가`, 삭제 확인 팝업 제목은 `유형 삭제`로 정한다.

후속 확정: 삭제 조작은 Figma `rEWWpNGvEtk3BjqE1xqkOL / 386:15351`의 12×12 SVG로 표시한다. 기존 `AdminIcon`의 `x-close`를 12px로 표시하면 동일한 픽셀이므로 재사용한다. 선택한 유형을 삭제하면 선택값을 비우고, 같은 이름의 유형을 다시 직접 추가할 수 있다.

삭제가 완료되면 어드민의 유형 선택·필터 목록과 사용자 `/blog`의 카테고리·필터 목록에서 해당 유형을 제외한다. 사용자 웹에 삭제 버튼을 추가하지 않는다. 기존 카테고리 배치와 모바일 가로 스크롤은 유지하고, 캐시 때문에 삭제 유형이 남지 않도록 기존 블로그 캐시 갱신 경로에 연결한다.

| 해당 유형에 연결된 글 | 처리 | 팝업과 버튼 |
| --- | --- | --- |
| 게시된 글이 있음 | 삭제 불가 | `이미 발행된 블로그 글이 있어 삭제할 수 없는 유형입니다.` / `확인` |
| 게시된 글은 없고 임시저장 글이 있음 | 삭제 불가. 사용자의 후속 답변 반영 | `임시저장된 블로그 글이 있어 삭제할 수 없는 유형입니다.` / `확인` 하나 |
| 연결된 글이 하나도 없음 | 확인 후 유형만 삭제 | 첨부 문구 `블로그 유형을 삭제하시겠습니까?.` / `취소`, `삭제` |

첨부본의 삭제 확인 문구에는 `?.`가 함께 있다. 문장부호를 임의로 고치지 않고 와이어프레임 검토 때 확인한다. 게시 여부는 작성일이나 `published_at` 유무가 아니라 글의 `status`로 확인한다. 어떤 상태의 글이든 연결돼 있으면 삭제하지 않는다.

## 구현 전 확인할 사항

1. **수정 화면의 삭제 조작:** 승인된 신규 등록 화면에 삭제 아이콘을 표시한다. 수정 화면에는 유형 목록의 삭제 결과만 반영하고, 별도 삭제 조작은 추가하지 않는다.
2. **표기:** 삭제 확인 문구는 첨부본의 `?.`를 유지한다. 환불 문구에는 강제 줄바꿈을 추가하지 않고 기존 자연 줄바꿈을 유지한다.

이 항목들은 구현 승인을 받아도 자동으로 확정되지 않는다. 관련 없는 확정 작업은 독립적으로 진행할 수 있다.

## 주요 검증 관점

- 삭제한 기본 유형이 새로고침·재로그인·다른 관리자 세션에서 다시 나타나는 경우를 검사한다.
- 임시저장만 존재하거나 게시 글과 임시저장 글이 함께 있는 경우를 검사한다. 작성일이 있는 임시저장 글도 삭제를 차단한다.
- `브로슈어·카탈로그`와 `브로슈어 · 카탈로그`, 기존 유형 ID, 사용자 정의 유형의 대소문자 차이를 같은 기준으로 비교한다.
- 처음 확인한 뒤 다른 관리자가 글을 연결한 경우, 실제 삭제 시점의 DB 검사로 삭제를 차단한다. 조회·저장 실패를 삭제 가능 상태로 취급하지 않는다.
- 공용 선택 컴포넌트와 대화상자를 확장해도 기존 상품·포트폴리오·공지·후기의 선택·저장·삭제 동작이 유지되는지 검사한다.

## 작업 3: 블로그 유형 삭제의 서버 저장과 차단 조건

**예정 파일과 역할:**

| 파일 | 역할 |
| --- | --- |
| `supabase/migrations/`의 신규 `blog_type_deletions` 마이그레이션 | 블로그 전용 삭제 내역과 관리자 접근 제한, 연결 글 검사 후 삭제 내역을 저장하는 DB 함수. 실제 파일명은 구현 때 `supabase migration new blog_type_deletions`로 생성한다. |
| `packages/supabase/src/blogTypes.ts` | 관리자 삭제 내역 조회와 삭제 요청. |
| `packages/supabase/src/categories.ts` | 삭제 내역을 전달한 호출에서만 유형 목록을 걸러내는 선택 매개변수. 기존 호출의 기본 결과는 유지한다. |
| `packages/supabase/src/index.ts`, `packages/supabase/src/types.ts` | 공개 함수 재수출, DB 테이블·함수 타입. |
| `packages/supabase/tests/blog-types.test.mjs`, `packages/supabase/tests/blog-type-deletions.sql`, `packages/supabase/tests/categories.test.mjs` | 접근 권한·조건 분기·목록 복원 방지·정규화·DB 검사 검증. |

**예정 인터페이스:**

```ts
listDeletedBlogTypes(client: CBrainSupabaseClient): Promise<string[]>
deleteBlogType(client: CBrainSupabaseClient, type: string): Promise<'deleted' | 'blocked_published' | 'blocked_draft'>
restoreBlogType(client: CBrainSupabaseClient, type: string): Promise<void>
getBlogCategoryOptions(values: readonly string[], deletedTypes?: readonly string[]): string[]
```

**저장 원칙:** 삭제 내역은 정규화한 유형 키로 저장한다. 게시물 행을 삭제하거나 `posts.type`을 일괄 변경하지 않는다. 기본 유형과 사용자 정의 유형 모두 삭제 내역으로 걸러낸다. 기본 상품 유형을 코드에서 지우거나 브라우저 `localStorage`에만 삭제 결과를 저장하지 않는다. 같은 이름 재추가는 명시적인 복원 요청으로 처리한다. 저장 키는 이미 별칭 해석을 마쳤으므로 다시 상품 ID로 변환하지 않는다.

DB 경계는 `public.blog_type_deletions(type_key text primary key)`와 `delete_blog_type(target_type text) returns text`로 둔다. 반환값은 위 `deleteBlogType()`의 세 결과와 일치시킨다. 검사 대상은 `posts.kind = 'blog'`인 연결 글이며, 같은 유형명을 사용하는 공지 글은 차단 근거로 삼지 않는다. 빈 유형과 `전체`는 삭제 입력으로 받지 않는다. 예외는 성공 결과로 변환하지 않고 호출자에게 전달한다.

- [ ] 대상 운영 DB의 실제 테이블·함수·권한과 마이그레이션 적용 방식을 조회한다. 현재 로컬 SQL에는 `site_settings` 생성 정의가 없어 그 테이블의 존재를 전제로 하지 않는다. 구현 전에 Supabase 최신 변경 내역과 관련 공식 문서를 확인한다.
- [ ] 삭제 내역 적용 시 기본/사용자 정의 유형이 제외되고, 기존 매개변수 하나로 호출하면 원래 결과가 유지되는 테스트를 추가한다. 정규화 차이와 중복, `전체`, 빈 문자열도 검사한다.
