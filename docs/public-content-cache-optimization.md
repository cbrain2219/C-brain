# 공개 콘텐츠 조회·캐시 최적화 기록

- 작성일: 2026-09-27
- 적용 커밋: [`620dcda`](https://github.com/cbrain2219/C-brain/commit/620dcda0045fe143616b730b2301177a852365b7)
- 적용 범위: 사용자 웹의 블로그·포트폴리오 조회, 어드민의 저장·삭제·정렬 후 캐시 갱신, Supabase 목록 조회 뷰
- 상태: 운영 DB 적용 및 사용자 웹·어드민 자동 배포 완료. 아래 수치는 배포 당시 검증 기록이다.

## 1. 문제와 원인

Supabase 요금제를 낮추기 전에 데이터 전송량을 줄일 필요가 있었다. 사용자가 제공한 당시 사용량 화면에는 일반 Egress 약 23.316 GB, Cached Egress 약 2.331 GB가 표시됐다. 같은 화면에서 Edge Function 호출은 0회였다. 따라서 과거 장애의 원인을 Edge Function으로 확정할 근거는 없으며, 일반 Egress 전체가 이번 콘텐츠 조회에서 발생했다고 단정할 수도 없다.

코드에서 확인한 문제는 다음과 같다.

| 문제 | 기존 동작 | 영향 |
| --- | --- | --- |
| 목록에도 전체 본문을 가져옴 | 공개 글 전체의 `content`와 관련 필드를 조회한 뒤 서버에서 목록 정보와 본문을 분리 | 목록에 불필요한 HTML 등의 전송 반복 |
| 상세 한 건을 보기 위해 전체 본문을 가져옴 | 전체 목록에서 slug가 일치하는 글을 찾음 | 게시물 수와 본문 크기가 늘수록 조회 용량 증가 |
| 요청 사이에 조회 결과를 공유하지 않음 | `React.cache`로 같은 서버 요청 안에서 중복 조회를 줄임 | 다른 방문자의 요청에서는 다시 Supabase 조회 |
| 긴 캐시와 관리자 수정의 연결 필요 | 어드민이 DB에 직접 저장 | 공유 캐시를 추가하기만 하면 수정 내용이 오래 남은 캐시에 가려질 수 있음 |

`useMemo`는 클라이언트 컴포넌트의 계산 재사용 수단이므로, 방문자 사이에 서버 DB 조회 결과를 공유해야 하는 이 문제의 해결책이 아니다.

## 2. 적용한 해결책

### 목록과 상세 조회 분리

- 목록은 `published_post_summaries`, `published_portfolio_summaries` 뷰를 조회한다.
- 블로그 목록은 짧은 `content_preview`, 포트폴리오 목록은 기존 설명과 동일한 의미의 일반 텍스트 `content_description`을 사용한다. 포트폴리오 설명 전체가 짧게 잘리는 것은 아니다.
- 전체 HTML 본문과 편집용 데이터는 목록 응답에서 제외한다. 이미지 경로 등 목록에 필요한 기존 정보는 유지한다.
- 상세는 기존 단건 조회 함수를 재사용해 해당 slug의 게시물만 가져온다. 관련 글 영역은 별도로 캐시된 목록 정보를 사용한다.
- 원본 게시물·HTML·이미지를 압축하거나 수정하는 데이터 변환 작업은 하지 않았다.
- 두 뷰는 `security_invoker = true`로 기존 원본 테이블의 RLS를 적용하고, 공개 상태인 행만 대상으로 한다.

### 요청 사이에 24시간 데이터 캐시 공유

- Next.js `unstable_cache`에 `revalidate: 86400`을 설정했다.
- 캐시는 블로그 목록, 포트폴리오 목록, 각 종류의 slug별 상세로 나눈다. 키에 Supabase 프로젝트 URL도 포함한다.
- `React.cache`는 유지해 같은 서버 요청에서 메타데이터와 화면이 요청하는 동일한 상세 결과도 재사용한다.
- DB 조회 실패는 지속 캐시 밖에서 처리한다. 일시적인 실패를 정상적인 빈 목록으로 24시간 저장하지 않는다.
- 큰 본문은 Node.js의 gzip/base64로 캐시에 저장하고 읽을 때 복원한다. 콘텐츠는 무손실 복원되며 이미지 화질과는 관계없다.

24시간은 재검증 간격이다. 전 세계에서 반드시 하루에 한 번만 DB 조회한다거나, 캐시가 영구 보존된다는 보장은 아니다. 새 키, 캐시 누락, 무효화 등으로 다시 조회할 수 있다. 이번 설정은 이미지 최적화 캐시의 1년 보관 설정과도 별개다.

### 관리자 변경 후 필요한 캐시만 무효화

어드민에서 DB 저장이 성공한 다음 `POST /api/admin/content/revalidate`를 호출한다.

| 관리자 작업 | 무효화 대상 | 유지하는 캐시 |
| --- | --- | --- |
| 블로그 저장·공개 상태 변경·삭제 | 블로그 목록 + 해당 글 상세 | 다른 블로그 상세, 포트폴리오 캐시 |
| 포트폴리오 저장·공개 상태 변경·삭제 | 포트폴리오 목록 + 해당 항목 상세 | 다른 포트폴리오 상세, 블로그 캐시 |
| slug 변경 | 해당 종류 목록 + 이전 slug와 새 slug 상세 | 무관한 상세 |
| 목록 순서 변경 | 해당 종류 목록 | 모든 상세 |

목록은 해당 종류 전체가 하나의 캐시이므로, 글 하나를 저장해도 그 종류의 목록은 다시 조회한다. 모든 게시글의 상세 캐시를 한꺼번에 비우지는 않는다. 이미 열려 있는 방문자의 화면을 강제로 갱신하는 기능은 아니며, 이후 서버 조회에 반영된다.

- 기존 관리자 인증을 재사용한다. 허용된 `ADMIN_APP_URL` Origin, 유효한 사용자 토큰, `app_metadata.role === 'admin'`을 확인한다.
- 요청 대상은 `blog` 또는 `portfolio`, slug는 최대 2개로 제한한다. 임의 경로나 태그를 전달해 전체 캐시를 비우는 API가 아니다.
- 갱신 요청은 회당 5초 제한으로 최대 2회 시도한다. 4xx 오류는 재시도하지 않는다.
- 갱신 실패 시 저장 성공과 별도로 안내한다. 이미 저장된 데이터나 새 이미지를 되돌리거나 삭제하지 않는다.

## 3. 확인된 효과와 해석 범위

### 운영에서 직접 확인한 결과

배포 후 캐시가 채워진 상태에서 블로그 목록과 포트폴리오 목록을 각각 3회씩 순차 요청했다. 6개 응답 모두 HTTP 200이며 예상 콘텐츠가 포함됐다. 해당 목록 조회의 `pg_stat_statements.calls`는 다음과 같았다.

| 목록 쿼리 | 반복 요청 전 | 반복 요청 후 | 증가량 |
| --- | ---: | ---: | ---: |
| 블로그 요약 조회 | 8 | 8 | 0 |
| 포트폴리오 요약 조회 | 8 | 8 | 0 |

측정한 서울 리전 요청에서 목록 캐시가 재사용됐다는 증거다. 모든 API의 DB 조회가 0회라는 의미는 아니다.

배포 당시 공개 블로그는 9개, 포트폴리오는 341개였다. 상세의 전체 본문 조회 대상은 기존 전체 9개/341개에서 해당 1개로 바뀌었다. **포트폴리오 본문 개수 기준 약 99.7% 감소이며, 응답 바이트·페이지 로딩 시간·전체 Egress·요금의 99.7% 감소를 측정한 것은 아니다.** 상세 캐시 적중 시에는 해당 단건 조회도 생략한다.

익명 권한으로 확인한 게시물 요약 뷰는 공지 등 다른 종류를 포함해 12행이었다. 블로그 화면의 9개와 집계 범위가 다르다.

### 아직 확정하지 않은 수치

- 운영 데이터의 기존/변경 목록 응답 바이트 비교: 후속 측정에서 브라우저 연결 지연과 공개 REST 연결 실패로 확보하지 못했다.
- 월간 전체 Supabase Egress 절감률과 무료 요금제 유지 가능 여부: 배포 후 사용량이 더 필요하다.
- 페이지 로딩 시간 개선율: 전후 동일 조건의 속도 측정을 하지 않았다.
- 로컬 합성 데이터로 확인한 응답 축소 결과는 운영 데이터나 청구액 절감률로 사용하지 않는다.

이미지 파일 다운로드, 상품·공지 등 이번 공유 캐시 대상 밖의 조회, 어드민 사용량은 별도다. Supabase 전체 Egress에는 이러한 트래픽도 포함될 수 있으므로 콘텐츠 조회 감소율을 전체 사용량에 그대로 곱하면 안 된다. 요금제 자체는 이번 작업에서 변경하지 않았다.

## 4. 검증 결과

### 로컬

- 격리된 PostgreSQL·PostgREST·Next.js 환경에서 실제 HTTP 시나리오 9개 통과: 요청 간 캐시 공유, 목록 본문 제외, 상세별 무효화, 이전/새 slug, 공개 상태 변경·삭제, 정렬 시 목록만 갱신, 인증·Origin 제한, 일시적인 조회 실패 후 복구 등을 확인했다.
- 2,470,051바이트 HTML의 캐시 저장 제한을 발견해 무손실 압축을 적용했다. 수정 후 실제 서버에서 2회 요청에 DB 조회 1회를 확인했다.
- 격리된 테스트 데이터와 인증 응답으로 실제 어드민 폼에서 블로그·포트폴리오를 저장하고 공개 화면 반영을 확인했다. 운영 Auth를 사용한 저장 검증은 아니다.
- SQL 테스트로 비공개 행 제외, RLS 유지, 일반 텍스트 변환, 전체 본문 필드 제외를 확인했다.
- Supabase 테스트 89/89, 어드민 모델 테스트 159/159 및 단위 테스트 80/80 통과.
- 사용자 앱 테스트는 282/288 통과. 실패 6개는 변경 전에도 실패하던 블로그 이미지·히어로, FAQ 탐색, 랜딩 소개, 주문 페이지, 포트폴리오 그리드 관련 기존 UI/소스 단언이었다. 새 캐시 테스트 5개는 통과했다.
- 사용자 웹·어드민 프로덕션 빌드, 세 패키지의 타입 검사·린트 통과. 어드민 빌드에는 기존 번들 크기 경고가 있었다.

주요 재검증 명령은 저장소 루트에서 다음과 같다.

```sh
node --test apps/user/__tests__/public-content-cache.test.mjs
pnpm --filter admin exec vitest run src/lib/publicContentCache.test.ts
pnpm --filter @repo/supabase test
```

[SQL 검증 파일](../packages/supabase/tests/public-content-summaries.sql)은 테스트 행과 RLS 정책을 추가한 후 롤백한다. 파일 지침대로 관련 스키마·마이그레이션이 적용된 격리 테스트 DB에서만 실행한다. 실제 HTTP·브라우저 검증은 당시 임시 테스트 환경에서 수행했으며 해당 실행 환경은 저장소에 포함하지 않았다.

### 운영

- 새 뷰를 트랜잭션으로 먼저 적용한 후 `main` 푸시로 자동 배포했다. 원본 행 수정은 없었다.
- 사용자 웹과 어드민 모두 `620dcda` 배포 성공 및 운영 도메인 연결을 확인했다.
- 블로그·포트폴리오 목록과 대표 상세 본문, 로그인된 어드민 화면을 확인했다. 확인한 브라우저 화면에서 콘솔 오류는 수집되지 않았다.
- 익명 역할의 요약 뷰 조회 성공, `security_invoker=true`, 전체 본문 필드 제외를 확인했다.
- 캐시 갱신 API: 정상 어드민 Origin의 OPTIONS 204, 토큰 없는 POST 401, 외부 Origin POST 403을 확인했다.
- 운영 어드민 번들에 새 캐시 갱신 호출이 포함된 것을 확인했다.
- **운영 게시물 저장·삭제 및 인증된 캐시 갱신 성공 요청은 실행하지 않았다.** 저장 후 무효화의 전체 흐름은 로컬에서 검증했다.

## 5. 남은 제한과 확인 방법

1. **실제 전송량 절감 측정:** 배포일의 전후가 섞인 누적 합계 대신, 배포 후 온전한 날짜 구간의 일별 일반/Cached Egress를 비교한다. 방문량과 이미지 업로드·조회 변화도 함께 기록한다. 이번 작업에서는 자동 모니터링을 설정하지 않았다.
2. **긴 캐시의 갱신 경로:** Supabase SQL Editor 등 어드민 밖에서 직접 수정하면 자동 무효화가 실행되지 않는다. 이런 작업 후에는 기존 관리자 인증을 사용하는 갱신 경로를 통해 관련 목록·slug를 무효화해야 한다.
3. **갱신 실패:** 저장 완료 안내와 캐시 갱신 실패 안내를 구분한다. `VITE_USER_APP_URL`, `ADMIN_APP_URL`, 로그인 상태와 API 응답을 확인한다. 무효화 실패 상태에서는 시간 기반 재검증이 성공할 때까지 이전 내용이 남을 수 있다.
4. **큰 캐시 항목:** 압축/base64 및 캐시 직렬화 후에도 Next.js 항목 크기 제한을 넘는 콘텐츠는 캐시되지 않을 수 있다. 큰 본문 테스트를 유지하고 실제 초과 사례가 나오면 저장 단위를 나누는 방식 등을 검토한다.
5. **요금제 전환:** 이 배포만으로 무료 요금제 사용이 안전하다고 결론 내리지 않는다. 최신 요금제 한도와 DB·Storage 크기, 일반/Cached Egress 등 항목별 사용량을 확인해야 한다.

## 6. 배포·운영 참고

- 마이그레이션: [20260927000000_add_public_content_summaries.sql](../supabase/migrations/20260927000000_add_public_content_summaries.sql)
- 당시 Supabase 연결 도구에 프로젝트 권한이 없어 로그인된 대시보드의 SQL Editor로 적용했다. 운영 DB에는 `supabase_migrations.schema_migrations`가 없었으므로 별도 이력 테이블을 만들지는 않았다. 이후 CLI 마이그레이션 체계를 도입하면 실제 적용 스키마와 이력 정합성을 먼저 확인한다.
- 신규 환경에는 **DB 뷰 → 사용자 웹 → 어드민 연결 확인** 순서로 적용한다. 뷰가 없으면 새 목록 조회가 실패할 수 있다.
- 캐시 갱신 연결은 어드민의 `VITE_USER_APP_URL`과 사용자 웹의 `ADMIN_APP_URL`이 실제 운영 Origin과 일치해야 한다. 배포 당시 각각 `https://www.cbrain.kr`, `https://admin.cbrain.kr` 조합의 연결을 확인했다.
- 되돌릴 필요가 생기면 웹·어드민 변경을 함께 검토한다. 이전 앱은 새 뷰에 의존하지 않으므로 앱을 되돌리기 위해 원본 데이터나 뷰부터 삭제할 필요는 없다.
- 이번 커밋에는 별도 작업 중이던 이미지 컴포넌트·Sentry 변경을 포함하지 않았다.
